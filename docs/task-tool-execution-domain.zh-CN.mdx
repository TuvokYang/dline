description: "任务中的工具块如何执行：由 reducer 决策、由执行器执行，两者只通过命令与事件相遇。"
---

工具执行域负责任务中工具块的实际执行。它是按目标运行时架构从 Task 巨型对象中切出的第一个执行器：由 reducer 决策、由执行器执行，两者只通过命令与事件相遇。

源码位置：`src/core/task/executors/tool/`。

## 为何按域切分，而非搬迁方法

早先的做法是把 `src/core/task/index.ts` 中与工具相关的方法逐个迁走，但推进不下去：像助手消息呈现这样的成员，在同一个函数体内既处理流式文本又处理工具预览；而终结轮除工具执行外，还承担 provider 计数、上下文压缩记账与后继任务移交。按成员切，要么把无关职责一并拖走，要么把工具逻辑留在原地。

按职责切则没有这个矛盾：混合职责的成员留在原处充当编排，工具执行以命令的形式离开。

## 命令

reducer 为每个准入的块发出一条带全部参数的命令：

```ts
interface ToolRunCommand {
	commandId: string
	turnId?: string
	dlineTid: string
	mode?: "serial" | "parallel"
}
```

`mode` 由 reducer 解析——它是唯一知道串行不变量的地方。执行器不会读取它来做调度决策，它只是收到"一个块"或"一批块"，然后执行收到的内容。`turnId` 随命令传递，使得属于 reducer 已经离开的轮次的结果能被识别出来，而不是被静默应用。

这取代了此前只携带块标识的裸效果：那种形式迫使接收方自行查找其余上下文，也让过期结果与当前结果无从区分。

## 执行器合同

```ts
handle(command: ToolRunCommand): void
halt(order: HaltOrder): Promise<void>
```

三个关键性质：

**`handle` 立即返回。** 调用方是串行化的运行时派发路径；在那里等待工具会让后续所有事件都堵在最慢的那个工具后面。

**所有结果都变成事件。** 成功发出 `tool.block_result`，抛错的工具发出 `tool.block_failed`，停止后到达的命令发出 `tool.rejected`。没有任何东西以未处理的 rejection 形式逃逸，执行器也从不直接写状态。

**`halt` 是排空屏障，而非提示。** 只有在在飞工作结算、且自有资源释放之后，才会发出 `tool.halted` 回执。回执之后该域不再产生任何输出。停止之前产生的结果会被丢弃而非应用，因此一个恰好在拆除期间完成的工具，无法让已取消的轮次复活。

## 资源所有权

该域拥有自己使用的工作区资源，`release` 是唯一的释放者：

```ts
interface OwnedToolResources {
	revertDiff(): Promise<void>
	cancelCommand(): Promise<void>
}
```

此前同一职责分散在 abort、interrupt、terminate 与 provider 重试四条路径上，每条都必须记得回退 diff。漏掉一条就留下打开的编辑器，重复一次就回退两遍。让所有停止都经过单一 release，使"每次停止恰好复位一次"成为结构性保证：该域保证每个停止代际只释放一次，使用相同 `haltId` 的重复取消是空操作。

释放失败会被上报但绝不重新抛出，因为运行时仍然需要回执才能确认该域已静默。即使第一项复位失败，第二项也会照常尝试，避免一个卡住的句柄让另一个资源一直处于打开状态。

## 能力由装配决定

UI 绑定能力在装配该域时授予，而不是在每个 handler 内部判断：

```ts
type ToolDomainSurface = UserFacingSurface | DeniedSurface
```

主任务以 user-facing surface 装配；分离式执行（例如子代理）以 denied surface 装配，此时 `ask`、`say`、`openInteraction` 与可见 diff 对它而言根本不存在。

这个区别之所以重要，是因为另一种做法是枚举。覆盖一份已知的回调清单，只能保护有人记得覆盖的那几个；每新增一个回调或 handler，问题就重新出现一次。而不给 surface 是移除能力本身，因此即使某个 handler 日后产生了 UI 需求，它依然无法触达主任务。

拒绝是显式的，不是静默空操作：真正需要用户参与的工作会以 `SurfaceDeniedError` 明确失败，并指明被拒的能力与原因，而不是看似成功、实则把输出投递到了错误的地方。

拒绝 surface 不会禁用工作本身。分离式执行照常写入文件，只是不做渲染。

## 与整体运行时收敛的关系

本域是目标架构中某一个执行器的先遣实现，不是对它的替代。此处交付的范围：

- 工具域本体，以及 `tool.*` 命令与事件词汇；
- 仅限本域的资源所有权与停止回执。

仍归属整体运行时收敛工作的部分：统一内核、取代当前运行时派发的事件循环，以及 provider、dialog、compose、background 与 cotask 执行器。

## 测试

行为由 `src/core/task/executors/tool/__tests__/` 下的聚焦单元测试覆盖：

- `handle` 在块结算之前返回，且一批块并发执行；
- 抛错的工具变成失败事件，而非逃逸的 rejection；
- 停止回执在排空之后到达，停止前的结果被丢弃；
- 重复取消只释放一次资源，而新的停止代际会再次释放；
- denied surface 拒绝全部能力，但工具照常执行。
