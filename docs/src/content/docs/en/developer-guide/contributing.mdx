Contributions of code, tests, documentation, and reviews are welcome. Everyone taking part must follow the repository's [Code of Conduct](https://github.com/TuvokYang/dline/blob/dev/CODE_OF_CONDUCT.md).

## Reporting issues

Before filing, [search existing issues](https://github.com/TuvokYang/dline/issues) to avoid duplicates. When creating a new issue, pick the matching template.

<Aside type="caution" title="Security vulnerabilities">
Report a security vulnerability privately through GitHub's [security advisory feature](https://github.com/TuvokYang/dline/security/advisories/new) instead of opening a public issue.
</Aside>

## Before you start

Except for small bug fixes, typo corrections, wording tweaks, and simple type fixes that do not change behavior, every contribution should start from a GitHub issue. Propose new features in the [Feature Requests discussions](https://github.com/TuvokYang/dline/discussions/categories/feature-requests) and wait for approval from the core maintainers before implementing them. Pull requests without an approved issue may be closed.

For a first contribution, look at issues labeled [good first issue](https://github.com/TuvokYang/dline/labels/good%20first%20issue) or [help wanted](https://github.com/TuvokYang/dline/labels/help%20wanted).

## Branches and pull requests

The repository has two long-lived branches:

| Branch | Role |
|---|---|
| `dev` | The integration branch and the target of every ordinary pull request |
| `main` | The production branch; it only receives a `dev` that has passed the full release gate |

<Steps>

1. Create an independent branch from the latest `dev`, such as `feature/<name>`, `bugfix/<name>`, `docs/<name>`, `refactor/<name>`, or `chore/<name>`.
2. Make your changes and verify them locally as described in [Development Setup](/en/developer-guide/setup/) and [Testing](/en/developer-guide/testing/).
3. Rebase your branch on the latest `dev` before submitting.
4. Push the branch and open a pull request against `dev`. CI runs type checking, lint, tests, and packaging.

</Steps>

Feature and bug-fix branches must not target `main` directly.

## Pre-submit checks

- Keep each pull request to one feature or one fix; split larger changes into several related pull requests, and split commits logically so they can be reviewed separately.
- Run `npm run lint` to check the code and `npm run format:fix` to fix formatting. `npm run format` only checks and does not write.
- Add tests for new features, update existing tests your change affects, and run the relevant tests.
- Make sure the branch builds, and remove debugging code and stray log output.

The pull request description should explain what changed, how to test it, and any breaking changes; include screenshots for UI changes.

## Commit messages

Use the Conventional Commits format, such as `feat:`, `fix:`, or `docs:`, and reference issues with `#<issue-number>` where relevant. The repository has no hook that validates commit messages; this is a convention rather than an enforced check.

## Changelog and versions

Contributors do not write changelog entries in pull requests. Maintainers handle version numbers and the changelog at release time: the Chinese edition is `CHANGELOG.md` in the repository root, and the English edition is `docs/changelog/CHANGELOG_en.md`. When a tagged version is packaged, both changelogs must contain the matching `## [X.Y.Z]` heading.

## Changing the documentation

This site is a separate Astro Starlight project under `docs/` and requires Node.js `>=22.12.0`:

```bash
cd docs
npm install
npm run dev      # local preview served at /
npm run verify   # unit tests, content checks, build, and output checks
```

You can also run `npm run docs`, `npm run docs:check`, and `npm run docs:verify` from the repository root.

Documentation must be submitted in Chinese and English pairs: Chinese pages go in `docs/src/content/docs/`, and English pages go in the same path under `docs/src/content/docs/en/`. `npm run check` verifies that the two languages match page for page and that links and components follow the site rules. Behavior, defaults, and UI text on a page should match the current code.
