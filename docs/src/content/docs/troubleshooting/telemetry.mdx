title: Telemetry and Issue Diagnostics
description: Choose whether Dline sends usage counts and error diagnostics, what each choice includes, where the data goes, and what turning it off deletes.
---

Dline asks for permission to send usage reporting and error diagnostics separately. The two checkboxes in **Settings → About** set the effective level, but they stay independent.

## Reporting levels

Open **Settings → About** and find **Allow usage reporting** and **Allow error reporting**. Both are checked by default. Unchecking either one denies that channel immediately, and an `unset` value also denies it.

| Effective level | Usage | Errors | What it covers |
|---|---|:--:|---|
| **Level 0: Off** | Off | Off | Nothing leaves your machine. A small local process ledger stays for crash recovery. |
| **Level 1: Usage** | On | Off | Content-free counts: Dline and model usage, request and tool outcomes, and token and cache usage. |
| **Level 2: Diagnostics** | Off | On | Crashes, exceptions, health warnings, and lifecycle signals, plus manual export of a local diagnostic bundle. |
| **Level 3: Usage + Diagnostics** | On | On | Both of the above. Neither includes prompts, files, commands, model responses, or raw artifacts. |

Organization policy can force either channel off but cannot turn one on. VS Code's `telemetry.telemetryLevel` can narrow delivery further; it never widens what you allowed here.

Your account is a separate channel. It follows usage consent and is never attached to ordinary usage or diagnostic records.

### Telemetry requirements for experimental features

Rollout participation in a regular release build requires both **Allow usage reporting** and **Allow error reporting**, plus a host such as VS Code or VSCodium that actually permits full telemetry (`telemetry.telemetryLevel` set to `all`). See [Experimental Features](/features/experimental/) for the full participation requirements and settings entries.

## What is sent

**Usage reporting** carries bounded dimensions and numbers: Dline version, editor and operating-system type, provider and model names, task and tool outcomes, durations, retries, and token and cache usage. It does not include conversations, file contents, paths, or commands.

**Error reporting** carries failure and health signals: the exception type and a safe code, severity, lifecycle reasons, CPU, memory, and queue figures, and evidence that a previous process ended unexpectedly. A hard crash or `SIGKILL` does not guarantee a usable stack trace.

Custom model and provider IDs are sent as you typed them. Do not put account numbers, customer names, repository names, or secrets into a custom model ID.

## Where data goes

- Canonical event, metric, and trace records can be written locally as JSONL.
- The default network destination is the local endpoint `http://127.0.0.1:4318`.
- When usage reporting is on, aggregated usage counts are sent to `https://otel.dline.cc`. When error reporting is on, aggregated error and runtime diagnostics go there too. No other channel uses that service, and no other destination falls back to it.
- An organization-configured endpoint receives consented usage signals only.


## Device identity

Dline identifies your installation with a random device secret, created on the first send and stored with owner-only permissions under the Dline data root. Signing in, signing out, or switching accounts does not change it, and it is never used as your account identity. Delivery to `otel.dline.cc` excludes both the device identifier and your account.

## Turning reporting off

When a condition for delivery stops being met, Dline aborts the current send and deletes unsent data and the local access token for that channel. The device secret is kept, so turning reporting back on does not register a new device.

Unchecking a box deletes that channel's unsent records, but it does not delete data the service already accepted. Error and usage channels are affected independently.

## Diagnostic bundles and `/reportbug`

**Export diagnostic bundle** writes a redacted ZIP locally while error reporting is enabled. Nothing uploads it automatically; review it before attaching it anywhere.

The current `/reportbug` handler asks for `api_request_output` and `additional_context`, and shows both in Dline's approval preview. After you approve, `api_request_output` is placed in the prefilled GitHub Issue form and passed through the browser URL. GitHub receives nothing until you review that form and submit it, so you can edit or remove the field first. Nothing is sent to `otel.dline.cc` this way, and no journals or ZIP files are uploaded.

Time-limited, Issue-specific diagnostic authorization is not available yet. Such diagnostics require your explicit request and separate authorization, and exclude prompts, code, command text, model output, credentials, and raw artifacts.

For the policy behind these choices, see the [Dline Privacy Policy](/privacy/).
