Contributions of code, tests, documentation, and reviews are welcome. Everyone taking part must follow the repository's [Code of Conduct](https://github.com/TuvokYang/dline/blob/dev/CODE_OF_CONDUCT.md).

## Reporting issues

Before filing, [search existing issues](https://github.com/TuvokYang/dline/issues) to avoid duplicates. When creating a new issue, pick the matching template.

<Aside type="caution" title="Security vulnerabilities">
Follow [Report a Security Vulnerability](/security/) instead of opening a public issue.
</Aside>

## Before you start

Except for small bug fixes, typo corrections, wording tweaks, and simple type fixes that do not change behavior, every contribution should start from a GitHub issue. Propose new features in the [Feature Requests discussions](https://github.com/TuvokYang/dline/discussions/categories/feature-requests) and wait for approval from the core maintainers before implementing them. Pull requests without an approved issue may be closed.

For a first contribution, look at issues labeled [good first issue](https://github.com/TuvokYang/dline/labels/good%20first%20issue) or [help wanted](https://github.com/TuvokYang/dline/labels/help%20wanted).

## Branches and pull requests

The repository has two long-lived branches:

| Branch | Role |
|---|---|
| `dev` | The integration branch and the target of every ordinary pull request |
| `main` | The production branch; it only receives a `dev` that has passed the full release gate |

<Steps>

1. Create an independent branch from the latest `dev`, such as `feature/<name>`, `bugfix/<name>`, `docs/<name>`, `refactor/<name>`, or `chore/<name>`.
2. Make your changes and verify them locally as described in [Development Setup](/developer-guide/setup/) and [Testing](/developer-guide/testing/).
3. Rebase your branch on the latest `dev` before submitting.
4. Push the branch and open a pull request against `dev`. CI runs type checking, lint, tests, and packaging.

</Steps>

Feature and bug-fix branches must not target `main` directly.

## Pre-submit checks

- Keep each pull request to one feature or one fix; split larger changes into several related pull requests, and split commits logically so they can be reviewed separately.
- Run `npm run lint` to check the code and `npm run format:fix` to fix formatting. `npm run format` only checks and does not write.
- Add tests for new features, update existing tests your change affects, and run the relevant tests.
- Make sure the branch builds, and remove debugging code and stray log output.

The pull request description should explain what changed, how to test it, and any breaking changes; include screenshots for UI changes.

## Commit messages

Use the Conventional Commits format, such as `feat:`, `fix:`, or `docs:`, and reference issues with `#<issue-number>` where relevant. The repository has no hook that validates commit messages; this is a convention rather than an enforced check.

## Changelog and versions

Contributors do not write changelog entries in pull requests. Maintainers own version numbers and the two current bodies: `CHANGELOG.md` (Chinese) and `docs/changelog/CHANGELOG_en.md` (English). Each file is the whole current changelog and holds exactly one section with the same name in both languages: `## [Unreleased]` during development, or one exact `## [X.Y.Z]` once that version is frozen and matches the manifest. It never holds an old version next to `Unreleased`, stacks several versions, or uses links instead of the body.

Older versions live in `docs/changelog/history.zh-CN.md` and `docs/changelog/history.en.md`: one history file per language with one section per archived version, not one directory per version.

Prepare the next version in this order:

1. Verify the current section, target version and release baselines against implementation, tests and package/lock. Compare the section name and both top What's New sections with the existing package version before changing anything.
2. Run the read-only check, then append the older exact version if current still holds one, using its version for `<current-version>`:

   ```text
   npm run changelog:check
   npm run changelog:append -- --version <current-version> --dry-run
   npm run changelog:append -- --version <current-version>
   ```

3. Confirm both history files. Replace the single current section in both bodies: either the older exact version you just appended, or the cumulative `Unreleased` section after checking the baseline and the final net change and renaming it to the exact candidate. Use real, curated target-version changes; do not keep the old section alongside it or relabel its body as the new version.
4. Synchronize package/lock and both What's New editions to the target, then run the checks below and review all six release facts: package, lockfile, both current section names and both top What's New versions. Both bodies must be non-empty and describe the same scope and order; a missing or mismatched current version blocks packaging, without falling back to history.

   ```text
   npm run changelog:check
   npx vitest run webview-ui/src/__tests__/vite-whats-new.test.ts
   ```

Normal append requires `--version <X.Y.Z>`, archives that frozen current into both history files and leaves current unchanged; it never archives `Unreleased`, changes package/lock or What's New, or publishes. Identical existing bilingual content is a no-op; differing text or unrelated missing versions are conflicts. The two history replacements are not a cross-file power-loss transaction. After interruption, inspect any remaining guard/temp first; a retry can complete only an identical partial prepend of the same frozen current version with otherwise paired history. Unknown state is never adopted. Check is read-only; builds, Insiders timestamps and temporary manifest edits never write history.

Keep `Unreleased` as the cumulative final net changes since the latest verified actual production publication. A pre-release snapshot follows its applicable delta range, but preparation does not clear that cumulative record. Production notes must include the final net changes from the production baseline, including pre-release work, not just the last delta or a concatenation of history. Only after verifying an actual production publication should maintainers adjust the baseline and remove what shipped, retaining later dev changes. Neither archive nor preparation assigns a publication date.

What's New is separately curated for every real version bump: a bare `## X.Y.Z` top heading, at most five highlights, each within 128 characters including its bold lead-in, and the same bilingual version, scope, order and item count. `## Unreleased`, placeholder highlights and automatic concatenation of changelog entries are not substitutes.

Preparation spans multiple files, not one atomic transaction. On an interrupted or inconsistent update, retain the complete history files, report the mismatch and stop packaging until repaired. Do not restore old notes under a new version or assume that `finally` cleanup can recover a power interruption.

## Changing the documentation

This site is a separate Astro Starlight project under `docs/` and requires Node.js `>=22.12.0`:

```bash
cd docs
npm install
npm run dev      # local preview served at /
npm run verify   # unit tests, content checks, build, and output checks
```

You can also run `npm run docs`, `npm run docs:check`, and `npm run docs:verify` from the repository root.

Documentation must be submitted in English and Chinese pairs: English pages go in `docs/src/content/docs/`, and Chinese pages go in the same path under `docs/src/content/docs/zh-cn/`.
