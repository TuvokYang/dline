Dline's target is one canonical telemetry mechanism. Loopback OTLP, local journals, account identity logs, planned `otel.dline.cc`, diagnostic bundles, and Issue diagnostics are sinks, views, or profile overlays of the same admission and privacy system.

See [Telemetry, Privacy, and Issue Diagnostics](/troubleshooting/telemetry/) for the public contract.

## Invariants

- Usage and error reporting are independent consents; `unset` is not consent.
- The `account` channel follows usage consent but is distinct from ordinary usage records.
- `distinct_id` is device/installation scoped and never changes on sign-in or account switch.
- Account and organization identity never enter ordinary Event/Metric attributes.
- Organization, host, server, and kill-switch policy can only narrow consent.
- Content, credentials, raw artifacts, and free-form exception prose do not enter canonical telemetry.
- Delivery failure never changes product outcomes.
- A transport outbox is sink state, not another telemetry source.
- `RuntimeSessionLedger` is a crash capsule, not Task lifecycle authority.

## Current pipeline

| Layer | Owner | Responsibility |
|---|---|---|
| Facade | `TelemetryService.ts` | Product-facing capture API |
| Recorders | `events/`, `instrumentation/`, Task observability | Produce typed facts |
| Early admission | `service/pipeline-port.ts` | Bounded bootstrap and runtime recording predicate |
| Consent | `service/channel-policy.ts` | Maps `usage` and `account` to usage consent; maps `error` and `runtime` to error consent |
| Context | `context/telemetry-context.ts` | Adds host metadata only; no account identity |
| Delivery | `service/provider-registry.ts` | Lazily materializes properties and fans out capabilities |
| Local canonical journal | `journal/` | OTLP-shaped Event, Metric, and Trace partitions |
| Runtime diagnostics | `runtime/` | Runtime producer, sampler, analysis, compatibility journal, bundle source |
| Crash capsule | `runtime/session-ledger.ts` | Bounded next-start process reconciliation |

The registry carries `usage`, `account`, `error`, `runtime`, and `raw-artifact` channels. The account channel is a dedicated `identify` delivery. Sinks must opt in explicitly.

## Device and account identity

`src/services/logging/distinctId.ts` owns one device-scoped value. Production code can set it only during initialization. `setDistinctIdForTesting()` exists solely for tests.

`TelemetrySignalDispatcher.identifyUser()` no longer mutates device identity or account-enriches `TelemetryContext`. It dispatches through `account`. Ordinary metrics now contain host metadata and metric dimensions only.

The default loopback registration declares `account` support. `OpenTelemetryTelemetryProvider.identifyUser()` emits one `account.identified` log for each account transition with `account_id`, `telemetry_channel=account`, and no `distinct_id`, display name, email, organization, or membership. Ordinary OTel events continue to receive device `distinct_id`.

PostHog account identification no longer mutates or aliases the device ID. The current PostHog usage registration and organization-configured OTLP registration do not opt into `account`, so they do not receive the account record.

## Current compatibility gaps

### Duplicate local persistence

`LocalJournalProvider` writes canonical `usage-*`, `metrics-*`, and `traces-*` files, each with a 4 MiB tail budget. While error reporting is enabled, `runtime/transports/session-journal.ts` also writes an unprefixed 1 MiB runtime tail.

The existing cleanup scans all `.jsonl` files in the shared directory, excludes only the exact active unprefixed runtime file, treats each remaining file as one item, keeps up to eight eligible files, and removes eligible files older than 3 days. It runs only when the error lifecycle starts. Do not describe this as an 8-session or global-byte bound.

### Split consent propagation

The canonical registry reads consent from `StateManager` for each delivery. The runtime compatibility lifecycle holds an enabled state updated at activation and through explicit error-setting changes. A live organization disable reaches the canonical registry through state replacement but does not currently call the runtime lifecycle transition. The single resolver migration must close this gap before remote rollout.

### Legacy pairing credential

Starting error diagnostics currently ensures an owner-only legacy pairing credential. No current transport consumes it. Issue diagnostics must migrate or discard it and require a new explicit per-Issue action.

## Target single mechanism

```text
normal signal ingress ─┐
authoritative usage ingress ─┤
account identity ingress ────┘
  -> one consent/profile resolver
  -> one channel/severity catalog
  -> canonicalization and baseline content policy
  -> sink-specific narrowing
  -> one provider registry
       -> one local journal owner
       -> loopback OTLP
       -> account-capable sink
       -> planned otel.dline.cc
       -> tests
  -> diagnostic bundle read view
```

Authoritative usage settlement remains a typed durable ingress because Provider totals require an awaited handoff, but it is governed by the same consent, policy epoch, channel catalog, privacy admission, and audit rules. It is not a second telemetry system.

The local-journal migration must first reproduce current file sizes, cleanup selection, ordering, crash evidence, cancellation, bundle export, and restart recovery. Only after parity may production stop duplicate compatibility writes. Any change to grouping, count, age, active-file protection, or byte budgets requires a separate approved storage contract.

<Aside type="caution">
Do not remove the compatibility writer first. The final stop-write step depends on canonical parity and historical readers.
</Aside>

## Planned remote profiles

- `usage`: content-free Provider token/cache/cost settlements and low-cardinality aggregates.
- `production`: content-safe `error` and `runtime` logs, metrics, and traces.
- `issue_diagnostic`: time-bounded diagnostic density requiring error consent and an active per-Issue grant.
- `development`: matching consent plus valid development enrollment.

The Dline remote provider attaches to the existing registry. It must not introduce a remote-only catalog or consent system. Remote diagnostics excludes both device `distinct_id` and account identity. A future account destination must be a separately declared account-capable sink.

Remote HTTP uses shared proxy-aware transport, fixed HTTPS origin, rejected redirects, bounded response reads, finite timeout, `AbortSignal`, and sanitized errors. Outboxes are bounded by count, bytes, and age, partitioned by profile, credential/token generation, grant, signal, and policy revision, and never source payloads from forensic journals.

Disabling a channel persists a stricter policy epoch first, stops capture and sends, aborts in-flight work, and deletes unsent remote outbox and local remote token for that channel. It does not delete accepted server data.

## Issue diagnostics

The host owns create, attach/check, and local-stop operations. Pairing secret, support code, consent marker, Issue token, journals, and bundle bytes never enter model context.

Ordinary Issue filing remains independent. Before Issue diagnostics release, `ReportBugHandler` must stop requiring and automatically placing `api_request_output` into the Issue `logs` field.

Authorization checks are user initiated, not polled. A maintainer-approved server grant has an expiry shown in UI. Invalid or failed checks leave the Issue stream off and preserve the base production profile. Local stop, expiry, consent disable, host/organization restriction, or kill switch deletes local Issue credential/outbox and stops delivery.

The service currently lacks a client revoke endpoint. Local stop cannot be described as remote grant revocation or deletion of already uploaded data. Issue rollout remains blocked until high-density scope enforcement and server retention/access/deletion policy are verified.

## Adding a signal

1. Register a stable event or metric name.
2. Assign channel and severity in the canonical catalog.
3. Record through the facade or a typed canonical ingress.
4. Keep fields bounded and content-free.
5. Decide explicitly whether an account-capable sink may receive it.
6. Add consent, identity-boundary, privacy-canary, journal, retry, and recovery tests as applicable.

Relevant tests include `TelemetryChannelPolicy.test.ts`, `TelemetryService.test.ts`, `OpenTelemetryTelemetryProvider.test.ts`, `distinctId.test.ts`, `LocalJournalProvider.test.ts`, `consent-boundary.test.ts`, `session-journal.test.ts`, and `bundle-builder.test.ts`.
