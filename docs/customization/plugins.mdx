## Planned Plugin Boundary

Future Dline plugins are expected to extend the host-neutral runtime without coupling plugin code directly to VS Code APIs. The public contract will be defined before plugin installation is exposed.

The design is expected to require:

- **Explicit capability declarations:** a plugin must declare the tools, lifecycle integrations, or UI contributions it needs.
- **No implicit approval:** installing or configuring a plugin must never bypass task-level approval and auto-approval policy.
- **Host-neutral contracts:** plugin behavior should work through Dline runtime interfaces so future hosts can implement the same contract.
- **Cancellation and bounded execution:** plugin-owned work must support cancellation, finite timeouts, and resource cleanup.
- **Recoverable state:** durable plugin activity must preserve stable identities and make interrupted work visible after restart.
- **Sanitized diagnostics:** errors and logs must not expose secrets, authorization headers, or unnecessary user data.

## Compatibility Commitments

Before the plugin surface becomes public, Dline will document and version:

- the manifest schema and capability identifiers;
- supported entry points and package isolation rules;
- lifecycle and hook ordering guarantees;
- configuration, storage, and secret ownership;
- compatibility and migration behavior across Dline releases;
- testing requirements for cancellation, failure, and restart recovery.

Until those contracts are published, do not build against internal plugin types, internal package paths, or undocumented descriptor formats.
